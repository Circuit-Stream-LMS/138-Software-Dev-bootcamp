Lesson 4 — Data Structures & Algorithms in JavaScript

Trees, Graphs & Finding Your Way Around

Quick recap: arrays are numbered rows, linked lists are chains of pointers, dictionaries look things up by key. Today's structures are different — they let one item connect to several others, not just the next one in line.

01 — Trees

A structure that branches

A tree is a data structure made of nodes, where each node can point to several "child" nodes below it. Every node has exactly one parent (except the very top one), and nothing ever loops back on itself.

Think of it like... A family tree, or the folder structure on your computer. One folder can contain several subfolders, each of those can contain more subfolders, and so on. You never find a folder that's somehow its own grandparent — trees only branch outward and downward.

A is the root. D, E, F, G have no children, so they're called leaves.

Root

The single node at the very top. Every tree has exactly one.

Parent / Child

A node directly above another is its parent; the one below is the child.

Leaf

A node with no children — the very end of a branch.

Depth

How many steps a node is from the root. The root's depth is 0.

Height

How many steps a node is from its furthest leaf below it.

A special kind: the Binary Search Tree

A binary tree is a tree where every node has at most two children — usually called "left" and "right." A Binary Search Tree (BST) adds one rule that makes searching fast: everything smaller than a node goes to its left, everything equal or bigger goes to its right. Follow that rule consistently, and you can find any value quickly by comparing and stepping left or right — similar to how you'd guess a number by narrowing "higher or lower" each time.

Where you already see trees

File systems

Folders inside folders inside folders — a tree, from root drive down.

Web pages

The HTML DOM is a tree: a page contains sections, which contain paragraphs, which contain words.

Fast lookups

BSTs power quick searching, similar in spirit to the dictionaries we covered last class.

02 — Graphs

What if connections don't have to branch neatly?

A graph is a more general version of a tree. It's just a set of nodes (also called vertices) connected by edges — but there's no root, no strict parent-child rule, and connections can loop back around.

Think of it like... Your friend group on social media. There's no "top" friend everyone descends from. People are just connected to each other, sometimes in circles — your friend's friend might also be your own friend directly.

A connects to B and C. C connects back to A and to D. Notice the loop A–B–D–C–A.

Directed vs. undirected

TypeMeaningReal example
UndirectedConnections go both waysFacebook friends — if you're my friend, I'm yours
DirectedConnections point one way onlyInstagram follows — you can follow someone who doesn't follow back

How does JavaScript store a graph?

The most common way is an adjacency list — really just a dictionary where each key is a node, and its value is the list of nodes it connects to. It reads almost like a sentence: "A connects to B and C."

In plain terms { A: ["B", "C"], B: ["A", "D"], C: ["A", "D"], D: ["B", "C"] } — each node lists its own neighbors, nothing more.

Where you already see graphs

Maps & navigation

Intersections are nodes, roads are edges — GPS apps search this graph for routes.

Social networks

People are nodes, friendships or follows are edges.

The internet

Web pages are nodes, links between them are edges — this is how search engines crawl the web.

03 — BFS & DFS

Visiting every node — but in what order?

"Traversal" just means visiting every node in a tree or graph, one at a time. There are two classic strategies, and they feel very different even though they visit the exact same nodes.

Our example graph for both walk-throughs below — A connects to B and C; B connects to D and E; C connects to F.

Breadth-First Search (BFS)

Visit all of A's neighbors first, then their neighbors, spreading outward one full ring at a time — like ripples in a pond.

Order visited A → B → C → D → E → F

BFS uses a queue (first in, first out) — the same structure we'd use for a line at the movies. It checks the oldest waiting node first.

Depth-First Search (DFS)

Pick one path and follow it as far as it goes, then backtrack and try the next path — like exploring a cave tunnel to its end before trying a different tunnel.

Order visited A → B → D → E → C → F

DFS naturally uses a stack (last in, first out) — or recursion

When would you use each?

GoalBetter choiceWhy
Shortest path (unweighted)BFSIt explores ring by ring, so the first time it reaches a node is guaranteed to be the shortest way there.
Explore everything, don't care about orderDFSUsually simpler to write with recursion, uses less memory for deep, narrow graphs.
"Is there any path from A to Z?"EitherBoth will find it eventually — they just explore in a different order.

Unweighted graph: every edge (connection) is treated as costing exactly 1 step, no matter what it actually represents. It doesn't matter if the connection is a short hop or a long one — in an unweighted graph, we just don't track that difference at all. All that matters is how many connections you crossed.

Weighted graph: every edge has a number attached — a cost, distance, time, or price — and that number matters. Some edges are "cheap" to cross, others are "expensive.

04 — Additional Algorithm (Dijkstra's)

What if some paths cost more than others?

BFS finds the shortest path by counting steps — it assumes every edge is equally "expensive." But real roads have different distances, and real flights have different prices. Dijkstra's algorithm finds the cheapest total path when edges have different costs, or weights.

Think of it like... Planning a road trip where every road has a toll. The straightest-looking road on the map isn't always the cheapest — sometimes a longer, roundabout route with cheaper tolls costs less overall. Dijkstra's algorithm is a careful way of comparing every option so you never overpay.

Where it's actually used

GPS & maps

Finding the fastest route when roads have different lengths and speed limits.

Network routing

Sending data through the internet via the least congested, fastest path.

Flight & travel search

Finding the cheapest combination of connecting flights or routes.

Games

Pathfinding for characters when some terrain is slower to cross than others.

The numbers on each edge are the "cost" to travel it. We want the cheapest total path from A to D.

The basic idea

  • 1Give the starting node a cost of 0, and every other node a cost of "unknown / infinity" for now.
  • 2Look at the cheapest node we haven't finished with yet, and check its neighbors.
  • 3For each neighbor, see if going through the current node is cheaper than what we had recorded before. If so, update it.
  • 4Mark the current node as finished, and repeat from step 2 with the next cheapest unfinished node.
  • 5Stop once every node is finished — you're left with the cheapest cost to reach each one.

Walking through our example

Starting at A, using the costs in the diagram above:

StepVisitWhat updatesBest known costs so far
1AB becomes 4, C becomes 2A=0, B=4, C=2, D=∞
2C (cheapest so far)Going A→C→B costs 3, cheaper than 4 — update B. Going A→C→D costs 10 — update D.A=0, B=3, C=2, D=10
3B (cheapest unfinished)Going A→C→B→D costs 8, cheaper than 10 — update D.A=0, B=3, C=2, D=8
4DNo cheaper option left.A=0, B=3, C=2, D=8

Final answer: the cheapest path from A to D costs 8, going A → C → B → D — even though the direct-looking A → B → D route would have cost 9. Comparing every option is exactly what makes this algorithm reliable.

The code

Here's the same five steps as actual JavaScript. The graph is stored as an adjacency list where each neighbor also has a cost attached:

// weighted graph — each neighbor has a cost attached
const weightedGraph = {
  A: { B: 4, C: 2 },
  B: { A: 4, C: 1, D: 5 },
  C: { A: 2, B: 1, D: 8 },
  D: { B: 5, C: 8 }
};

function dijkstra(graph, start) {
  let distances = {};   // cheapest known distance to each node
  let visited = new Set();
  let previous = {};    // how we reached each node, for rebuilding the path

  // Step 1: start = 0, everything else = infinity
  for (let node in graph) {
    distances[node] = Infinity;
    previous[node] = null;
  }
  distances[start] = 0;

  while (visited.size < Object.keys(graph).length) {
    // Step 2: pick the cheapest unvisited node
    let currentNode = null;
    let smallestDistance = Infinity;
    for (let node in distances) {
      if (!visited.has(node) && distances[node] < smallestDistance) {
        smallestDistance = distances[node];
        currentNode = node;
      }
    }
    if (currentNode === null) break; // nothing left to reach

    visited.add(currentNode);

    // Step 3: check if going through currentNode is cheaper for its neighbors
    for (let neighbor in graph[currentNode]) {
      let newDistance = distances[currentNode] + graph[currentNode][neighbor];
      if (newDistance < distances[neighbor]) {
        distances[neighbor] = newDistance;
        previous[neighbor] = currentNode;
      }
    }
  }

  return { distances, previous };
}

const result = dijkstra(weightedGraph, 'A');
console.log(result.distances);
// { A: 0, B: 3, C: 2, D: 8 }  ← matches the table above
How this connects to BFS If every edge cost exactly 1, Dijkstra's algorithm would behave exactly like BFS. BFS is really just Dijkstra's algorithm for the special case where nothing costs more than anything else.
